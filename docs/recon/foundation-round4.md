# Round 4 outstanding must-fixes

The foundation finished at 0/3 lenses passing. These are what the final round said still stands.

> Rounds 1-3 of motion review were conducted through a 1.6fps camera and are not trustworthy. Round 4 motion was measured with real animation events.

## Icons, type, states and form controls — AAA-BAR §4, §5, §7

stills 8/10, motion 9/10

**Worst:** The numeral role has no typeface of its own. `.num` in foundation.css sets `tabular-nums`, a `min-width` and an alignment — and nothing else: no family, no weight, no size, no tracking, no colour. Measured live on #uikit it computes to Segoe UI 12.8px/400, which is `.t-body` with different figures. So every number a player reads under pressure — cost, power, health, the turn timer, Clout, mission progress — is set in whatever UI font the OS ships: Segoe UI on Windows, something else on macOS, something else again on Android. Three different games. Chivo is already committed to the repo at 33 KB, and §4's own comment in that file chose it partly because "its digits are the same width at every weight *without* `tnum`" — then the one role that exists for digits does not use it. The same file argues, correctly and at length, that leaving the display face as "whatever Windows ships" was a ceiling on every screen in the game; it lifted that ceiling for headings and left it in place for numerals, which in a card game are the interface. Put the HYPEBOUND battle HUD beside Hearthstone's mana crystals or MTGA's counters and this is the first thing that answers §0's one-sentence test.

### 1. The numeral type role supplies none of the five things §A3 requires of a role. Measured on #uikit, `.num` renders as Segoe UI 12.8px weight 400 — indistinguishable from `.t-body` except for tabular figures — while `.t-display` and `.t-heading` are Chivo 800/600. The brand face is in the repo, was selected on the width behaviour of its digits, and is not used by the digits.

- **Where:** src/ui/theme/foundation.css:1087 (the `.num` block in §4)
- **Fix:** Give `.num` a face and a rank of its own inside the existing block: `font-family: var(--font-display); font-weight: 600; letter-spacing: 0; color: var(--text);` alongside the existing `font-variant-numeric`, `min-width` and `text-align`. Chivo's 200–900 axis is already loaded and its figures are same-width at every weight, so this costs no extra bytes and cannot reflow a slot that is already reserved by `--digits`. Then add a numeric row to the A3 panel in src/ui/screens/uiKitScreen.ts showing the same value in `.t-body` and in `.num` so the two hands are visible side by side, the way the display/heading pair already is.

### 2. The checkbox and radio tick is a second icon set living inside module A. `--tick` and `--tick-off` are `data:` SVGs drawn `m5 13 4.5 4.5L19 6.5` at **stroke-width 2.75** with `#ffffff` and `#8e88a4` baked in — a different path at a different weight from `uiIcons.ts`'s `check` (`M4.4 12.6 L9.8 18 L19.6 6.4` at 1.75). Painted at `background-size: 100%` of the 20px box its effective stroke is 2.29px against the set's 1.46px at the same size, and it carries none of the set's 2px optical padding, so it runs into the box corners. Photographed side by side at 4x they are plainly two different hands. The baked colour is also the exact failure the chevron comment forty lines above condemns: it cannot follow the accent or a colour-blind mode, so a tinted checkbox gets a white tick.

- **Where:** src/ui/theme/foundation.css:364 and :369 (`--tick` and `--tick-off` in §1)
- **Fix:** Regenerate both from the real artwork rather than redrawing it: `iconDataUri("check", "#ffffff")` and `iconDataUri("check", "#8e88a4")` from src/ui/art/uiIcons.ts already emit the correct path at ICON_STROKE with the set's padding — paste those two strings in, or export a tiny const from uiIcons.ts and inject them at boot. Then drop `background-size` for the mark layer from `100% 100%` to about `76%` so the 2px of grid padding survives the scale and the tick stops touching the corner. If the tick must read heavier than 1.75 inside a 20px well, scale the whole mark up rather than re-stroking it, so the family stays at one weight.

### 3. `<summary>` still renders the operating system's disclosure triangle, and it is live on the story screen. §A6 binds the kit to the elements themselves via `:where(input, select, textarea, button)` and never mentions `summary`; screens.css:1648 sets only `cursor` and `font-weight` on `.story-archive-capstone summary`. Captured at 4x: a native ▼, drawn by the engine at whatever weight it feels like, on a screen that owns 107 hand-drawn marks including `chevron-right` — the same class of thing the icon module exists to delete. `<progress>`, `<meter>`, `type=date`'s picker button, `type=color` and `type=file`'s grey "Choisir un fichier" button are all still fully native as well; nothing uses them today, but a rule that says "no route may ever render an OS widget" and covers six element types will be broken by the first screen that reaches for a seventh.

- **Where:** src/ui/theme/foundation.css:1653 (the §A6 element baseline)
- **Fix:** Extend the baseline in module A's own file — no other module's file needs touching. Add `:where(summary) { list-style: none; cursor: pointer; display: flex; align-items: center; gap: var(--sp-2); }`, `:where(summary)::-webkit-details-marker { display: none; }`, and draw the disclosure mark with the same `--chevron-arm-l/--chevron-arm-r` pair the select uses, rotated on `[open]` so it has a state. In the same block add `:where(progress, meter) { appearance: none; -webkit-appearance: none; }` with the `.mat-well` track and hero fill, plus `::-webkit-calendar-picker-indicator { filter: invert(1) opacity(.7) }` and `::-webkit-file-upload-button { appearance: none }` so the latent five cannot arrive white later.

### 4. `kw-spotlight` and `mode-lab` are the same picture at 24px. Both resolve to a narrow top widening into a splayed cone with a horizontal rule across the bottom: the spotlight's two beams read as the flask's shoulders, and the light pool's ellipse reads as the liquid line. The comment on `mode-lab` records three passes spent separating it from `attack` and moving its waist to a cone silhouette — which is precisely the silhouette `kw-spotlight` already had. Confirmed on my own pair sheet at a true 24px; it is the only pair of the thirty I tested that fails. (Second, softer note: `st-shielded` at 24px is effectively a plain ring — its specular arc sits directly on the circle and reads as a thickening of the stroke rather than as a second mark.)

- **Where:** src/ui/art/uiIcons.ts:441 (`kw-spotlight`), against :295 (`mode-lab`)
- **Fix:** Break the cone. Give `kw-spotlight` a tilted lamp head — rotate the trapezoid roughly -25° about its own centre and swing the beams with it — so the mark becomes an asymmetric diagonal rather than a symmetric funnel; a flask cannot lean. Alternatively drop the ellipse and let the beams end in open air, which removes the horizontal baseline that the flask's liquid line shares. Then re-run the contact sheet and check the new shape against `kw-afterparty` and `attack` before committing, since both live in the same cone-and-stem neighbourhood.

## Motion and the space between menus — AAA-BAR §3 and §3a

stills 8/10, motion 6/10

**Worst:** The transition is only ever drawn when the destination is cheap. The choreography itself is excellent — on lobby↔missions I measured a 101ms descend overlap, a 107ms ascend exchange, a parent that genuinely recedes (opacity 1→0.61, scale 1→0.974, blur 0→2.65px, brightness 1→0.849) and an ascend that returns from exactly those values — but shell.ts starts the animations and then blocks the main thread inside the destination's constructor, so on the routes players actually use the transition plays behind a frozen compositor and is never composited at all. Measured on lobby→collection: a 588ms long task at t=20, `nav-descend-out` firing animationstart and animationend in the same millisecond (652.5/652.6 — zero frames of recede), `nav-descend-in` not starting until t=1185, settled at **t=1863ms**, 4.4× the 420ms budget. What the player sees, reproduced in two independent screencasts (cd-15_t405.jpg, cd2-35_t728.jpg, cd2-38_t807.jpg, cd2-48_t978.jpg): the lobby dims to ~35% and holds under a bright horizontal seam for ~550ms, pumps back to full brightness, then a half-built Collection appears with an empty card grid, then the grid pops in. Coming back is worse — collection→lobby produced **1 rAF frame and zero animation events in a 1600ms window**, both screens pinned at their 0% keyframes (lobby at opacity 0, blur 7px, brightness 0.6 behind an opaque Collection); a Playwright screenshot of that state times out at 30s. And on #uikit, the foundation's own gallery, the same root cause produces the explicit non-negotiable: a frame containing **nothing but the atmosphere — no outgoing screen, no incoming screen** (uk-32_t640.jpg and uk2-32_t651.jpg, two separate runs). Per the brief's own rule that is an automatic fail. Separately on stills: the frames are strong — one 315° key, real materials, four resolvable planes, a lobby that is genuinely alive at rest — but the nine lobby destinations are still nine identical pills with a small centred icon, which is the flattest thing in any frame I captured; that call belongs to the craft lens, not this one, and is why stills sit at 8 rather than 9.

### 1. A frame with no screen in it. `retire()` correctly waits for both `animationEnded` and `released` before removing the outgoing root, but `nav-descend-out` has `animation-fill-mode: both` and ends at `opacity: 0` — so on an unveiled navigation whose constructor outruns the 170ms exit, the document holds exactly one screen and it is invisible. Reproduced twice on lobby→#uikit: uk-32_t640.jpg and uk2-32_t651.jpg are bare atmosphere, no lobby, no gallery. §3a's 'never a blank frame' is a non-negotiable.

- **Where:** src/ui/shell.ts:801 (retire) with the keyframe at src/ui/theme/transitions.css:1094
- **Fix:** End `nav-descend-out` and `nav-ascend-out` at a low but non-zero opacity (~0.12) instead of 0, so a held outgoing screen is still an image. The incoming child paints over the parent on a descend, so nothing is visible in the normal case; `complete()` already removes the element the moment `place()` releases it, so the ghost only ever exists during the window that is currently a hole.

### 2. `veiled` is computed from the destination only, so leaving a heavy screen is unprotected. collection→lobby measured 1 rAF frame and zero animationstart events in 1600ms — tearing down 245 card canvases blocks the ascend exactly as building them blocks the descend, and the most-pressed control in the menu tree draws not one frame of its transition.

- **Where:** src/ui/shell.ts:631
- **Fix:** Veil when either endpoint is heavy: `const veiled = outgoing !== null && !plan.reduced && (plan.relation === "curtain" || routeNode(id).heavy === true || routeNode(outgoing.id).heavy === true);`

### 3. The heavy veil does not cover the build. `partCurtain()` runs on the line after `place()`, before the incoming screen has painted, so the scrim parts onto a half-drawn screen — cd2-48_t978.jpg shows the Collection with its header and filter rail present and the entire card grid empty. The scrim is also too translucent to be a cover: the lobby stays legible through it for ~550ms and then pumps back to full brightness (cd2-38_t807.jpg) before the destination appears.

- **Where:** src/ui/shell.ts:668
- **Fix:** Await two frames after `place()` before `partCurtain()`, the same `twoFrames()` already used on the way in, so the curtain only opens on a composited destination. Raise the menu scrim's peak opacity to full occlusion — as drawn, its seam reads as a bright horizontal bar over a readable lobby rather than as a cover.

### 4. `uikit` is registered in main.ts but absent from ROUTES, so it falls to `UNKNOWN_ROUTE`, which is not heavy — while its constructor runs six long tasks totalling ~1.18s (33+96, 129+503, 650+90, 991+114, 1115+260, 1376+119). That is the route the blank frame appears on, and the forgiving default means every new screen the other builders add inherits the same unveiled path.

- **Where:** src/ui/shell.ts:145
- **Fix:** Add `uikit: { parent: "lobby", order: 19, room: "forge", heavy: true },` to the lobby's children. Consider also defaulting `UNKNOWN_ROUTE` to `heavy: true` — an unclassified screen is precisely the one whose build cost nobody has measured yet.

### 5. The settle cancels the cascade mid-flight. On lobby→missions, `animationcancel` fired at t=490.2 on three in-flight `nav-child-rise` animations and on `nav-ambient-in`, snapping those panels from ~83% progress straight to rest. The last cascade item starts at 60 + 10×30 = 360ms and runs 198ms, ending at 558ms, but `watchEntrance` writes `data-nav="settled"` before that. §3a: nothing pops.

- **Where:** src/ui/theme/transitions.css:1557
- **Fix:** Either cap the cascade so the last item lands inside the settle (six items per container, or 24ms steps), or have `watchEntrance` hold `data-nav` until the longest child-rise has ended rather than keying off the screen root's own animationend.

### 6. The foundation's own gallery does not demonstrate the cascade it ships. Zero `nav-child-rise` events fired on #uikit across two instrumented runs, because the rule reaches through `:is(header, nav, main, section, footer, [class*="-body"])` and the gallery's sections are not inside one of those. The gallery is also much quieter at rest than a real screen — ~5% of pixels changing over 400ms against the lobby's 20–40%.

- **Where:** src/ui/screens/uiKitScreen.ts:1
- **Fix:** Wrap the gallery's sections in a `<main class="uikit-body">` so it picks up the same default cascade every other screen gets, and let the atmosphere through at rest the way the lobby does, so the screen that exists to prove the motion system actually exhibits it.

### 7. The project's camera cannot photograph motion, which is why three rounds of this critique saw either nothing moving or an already-settled destination. `shot.mjs` launches Chrome with `--use-gl=angle --use-angle=swiftshader`, routing all compositing through software GL: measured 1.9fps on the lobby and a 3144ms screenshot, against 75.4fps and 459ms for the same page under default flags. Every `--frames 12x35` burst therefore samples roughly one frame per 500ms of a 380ms transition — the prescribed descend burst returned frame 0 = full lobby, frame 1 = fully settled collection.

- **Where:** scripts/shot.mjs:126
- **Fix:** Drop `--use-gl=angle` and `--use-angle=swiftshader` and keep only `--enable-unsafe-swiftshader` (measured 75.1fps, 447ms screenshots, WebGL still available for the battle route). Consider adding a `--cast` mode built on CDP `Page.startScreencast`, which returns real compositor frames with real timestamps instead of a sampled burst.

## Materials, depth and light (AAA-BAR §1, §2, §6, §7)

stills 8/10, motion 7/10

**Worst:** `.mat-panel` is simultaneously the container and the contents at one value, so the most frequent depth transition in the whole system carries no value change. Measured from a single frame of #uikit at 1:1: the section card's face is 35.3, and a `.mat-panel r-tile` sitting on it reads 40.9 at its lit top strip and ~32 across its mean — a raised object that throws a 9-level contact shadow onto a surface it does not out-value. Compare the chip, where the ladder works: chip-on-card is 53.5 vs 35.3, +18, and it reads instantly as an object lying on something. Squint the page (scripts/screenshots/review/sq-uikit.png) and the seven state tiles in the A4 row simply vanish — the whole screen resolves into one mid-purple mass with a few pink dashes, which is §6's named failure verbatim. Squint frame 60 of hearthstone_frames and you get a light sand mass, a dark carved surround, and every medallion still readable as a separate object, because in that reference value *is* height: the mat is lighter than the frame, the medallion lighter than the mat, the socket darker than both. Here the system already steps the radius for nesting — `--r-nested` exists and is used — but nothing steps the fill, so panel-in-panel-in-panel is one flat field held apart by a 1px rim and a shadow. That is stacking, not depth.

### 1. A nested `.mat-panel` is the same value as the `.mat-panel` it sits on, so raised structural furniture does not read as raised. The system steps the radius for nesting but not the fill.

- **Where:** src/ui/theme/foundation.css — the `--fill-panel` token (~line 246) and the `.mat-panel` rule (~line 770)
- **Fix:** Add a nesting rung to the value ladder the way the chip already has one. Introduce `--fill-panel-raised` a step lighter than `--fill-panel` (roughly `linear-gradient(var(--light-sweep), rgb(66 50 108 / .95) 0%, rgb(30 21 54 / .96) 100%)`, which lands a lit face near 50 against a card at 35) and apply it with `.mat-panel .mat-panel, .mat-panel .mat-hero` — or better, a `--depth` custom property the material rule reads, so three levels of nesting give three values instead of one. Target the same ~15-level step the chip gets, and re-run the squint test on #uikit: the seven tiles in the A4 row must still be findable as objects at 44px wide.

### 2. The specular sheen band is oriented along the key-light axis instead of square to it, so the one moving highlight in the system sweeps in from the corner opposite the key. The file's own comment states the intent correctly and the arithmetic delivers the opposite.

- **Where:** src/ui/theme/foundation.css ~line 521, `calc(var(--light-sweep) + 90deg)`
- **Fix:** Change `+ 90deg` to `- 90deg`. 225deg produces bands lying along the 315/135 diagonal — a `\` band, parallel to the key, travelling from the top-right corner to the bottom-left. 45deg produces a `/` band whose iso-lines match the fill's own iso-luminance lines and which travels top-left to bottom-right, away from the light. Proof is in scripts/screenshots/review/band-tall.png, where the sheen is pinned at 50% with the alpha cranked: the highlight runs top-left to bottom-right across a plate whose gradient is lightest at the top-left. Fix the surrounding comment too — "square to the key" is what 45deg gives, not 225deg.

### 3. `bevelStrip()`'s CSS form and its painted form do not match, which defeats the one thing the function exists for — the DOM HUD and the 3D mat sharing one edge treatment. The gallery puts them side by side as proof and they visibly disagree.

- **Where:** src/ui/art/texture.ts — `bevelStrip()`, both the `boxShadow` string and the canvas painter
- **Fix:** Measured on the gallery's own pair: CSS T-B 8.7 against painted T-B 15.4 (1.8x harder vertically) while L-R agrees at 25.7 vs 26.7, and at 8x (scripts/screenshots/review/r4-bev1.png vs r4-bev2.png) the painted form has no crisp rim line at all, a broad soft edge ramp instead of a 1px step, and a visibly larger effective corner radius. Make the canvas painter draw a 1-device-pixel hard rim and lip at the same alphas the box-shadow string emits, and derive both from one shared table of numbers so a test can assert the rendered top-minus-bottom of the two forms agree within a level or two.

### 4. The four axis-aligned zero-blur inset edges meet at the corner 45-degree bisectors with an order-of-magnitude alpha step and no interpolation, so every plate on the page carries a hard-cut black nick at its top-right and bottom-left corner.

- **Where:** src/ui/theme/foundation.css §3, the `--mat-cast` inset stack (~lines 639-650)
- **Fix:** The lit insets are 0.03 and 0.016 and the unlit ones are 0.345 and 0.19; where the top rim hands over to the right lip the edge jumps from +0.03 white to -0.19 black across a single arc pixel, which renders as a chopped black comma rather than a rim dying out. Replace the four with one continuous edge: paint a conic-gradient ring (or module B's bevel texture) into a `border: 1px solid transparent` with `background-origin/clip: border-box`, interpolating alpha from the lit value at the 135deg normal to the unlit value at 315deg. Visible at 4x on all five swatches in scripts/screenshots/review/r4-radii.png and isolated in c-panel-tr.png and c-panel-bl.png.

### 5. The idle sheen is below the threshold of perception, so the "alive at rest" claim is measurable rather than true. Two frames 440ms apart are indistinguishable by eye.

- **Where:** src/ui/theme/foundation.css — `@property --sheen-alpha` initial-value 0.009 (~line 102) and the sheen gradient's 42%/50%/58% stops
- **Fix:** At 0.009 the resting band lifts a panel face of ~32 by about 1.8 levels; a 20x amplified frame difference was needed to find it at all (scripts/screenshots/review/d-sheen-03.png is legible, d-sheen-g4.png at 4x gain is not). Roughly double the resting alpha to ~0.018-0.02 — about 11-12% of face, still half the hover catch's 18% so the two stay distinguishable — and widen the stops to roughly 30%/50%/70% so the ramp covers more of the plate and the crawl reads as light moving rather than as a hairline passing.
